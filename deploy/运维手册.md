# 运维手册 · 交通法规问答服务

> 配套：`docs/04_接口文档.md`（调用面）、`README.md`（对外总览）。本手册是部署与运营的作业面。
> 拓扑：单机 Docker（Windows + Docker Desktop 形态）；`web`(nginx，托管前端) + `app`(rag) + `agent` + Milvus 三件套同一 compose；宿主两个入口：**web（:3000）＝浏览器界面**（同源反代 `/health` `/qa` `/laws` `/documents` 到 agent），**agent（:8001）＝ API 直连**；rag 与应用库不进宿主网络面。目标环境＝内网 / 白名单，不面向公网。

## 1. 部署与升级

**首次部署**：在 `deploy/.env` 落两个键（该文件已 gitignore）：

```
MINIO_ROOT_USER=<强口令用户名>
MINIO_ROOT_PASSWORD=<强口令>
```

compose 插值读的是 **compose 文件所在目录** 的 `.env`（v5.4.0 实测；仓库根的 `.env` 不管用）。缺任一键，所有 compose 命令报 `required variable ... is missing`（提示语指向 `deploy/.env`）。

**起栈（生产面）**：

```bash
docker compose -f deploy/docker-compose.yml up -d
docker compose -f deploy/docker-compose.yml ps    # 等六个容器 healthy
```

宿主入口两个：8001（agent）与 3000（web 界面）；MinIO 凭据是 compose 必填插值，milvus 的凭据插值同源、自动跟随。**改口令流程**：改 `deploy/.env` → 停机重建 minio 与 standalone（`docker compose -f deploy/docker-compose.yml up -d --force-recreate minio standalone`）。

**改代码后重建**（镜像把源码烤进去了）：

```bash
deploy/build.sh
```

`build.sh` ＝ 直连 `docker buildx build --load` 三条 + `up -d --force-recreate --no-deps app agent web`。**禁用 `docker compose up --build`**（本机 compose v5.4.0 内嵌 bake 出错，报错表面像网络问题）与 `docker builder prune`。

**改前端后重建（web 服务）**：web 镜像只 COPY `frontend/dist`（构建产物不进版本库）。先在宿主 `cd frontend && npm ci && npm run build`，再跑 `deploy/build.sh`；只动前端时也可单独重建：

```bash
docker buildx build --load -t traffic-law-qa-web:0.1.0 -f frontend/Dockerfile .
docker compose -f deploy/docker-compose.yml up -d --force-recreate --no-deps web
```

**本地开发**（恢复全部宿主端口 8000/9000/9001/19530/9091 与默认 MinIO 凭据 minioadmin）：

```bash
docker compose -f deploy/docker-compose.yml -f deploy/docker-compose.dev.yml up -d
```

覆盖文件里字面值优先于 base 的插值（实测），所以开发面不依赖 `deploy/.env` 的强口令。

## 2. 日常巡检

- `docker compose -f deploy/docker-compose.yml ps`：六个容器 `healthy` 才算好。agent 的 healthcheck 读 `/health` **body**（要 `status==ok` 且内嵌 `rag.status==ok`，不是只看 200）；rag 断掉 agent 会变 unhealthy。
- **agent 长期 unhealthy 的处置**：启动时探不到 rag 留下的 `boot_error` 不自愈（进程活着，`restart: unless-stopped` 不触发）——先修 rag，再 `docker compose -f deploy/docker-compose.yml restart agent`。
- `docker compose -f deploy/docker-compose.yml logs -f --tail=200 agent`（或 `app`、`web`）。**应用日志一律 stdout/stderr**，由 docker json-file 驱动轮转（max-size 10m × 3 个文件/服务）；不要在容器内另写日志文件。
- `docker stats` 看内存；agent 是轻进程，重的是 app（本地嵌入与重排模型）。

## 3. 告警

**watchdog.sh**（判据与 compose healthcheck 一致；只打日志或 POST webhook）：

```bash
deploy/watchdog.sh              # 单次探测：健康 rc=0；失败 rc=1（宿主计划任务可依 rc 触发任务级告警）
deploy/watchdog.sh --loop 60    # 长驻：每 60 秒一轮
```

- **落法一（宿主计划任务）**：定时跑 `deploy/watchdog.sh`，失败 rc≠0；配 `WATCHDOG_WEBHOOK_URL` 时失败会 POST 告警 JSON（字段 `service/status/url/time/reason`，发送失败不改变退出码）。
- **落法二（Uptime Kuma 等）**：探 `http://<host>:8001/health`，判据同样读 body：`status==ok && rag.status==ok`。
- `WATCHDOG_URL` 换探测地址（默认 `http://127.0.0.1:8001`）；`WATCHDOG_PYTHON` 钉死解释器绝对路径（默认自动挑 python3 → python → 仓内 .venv，本机 python3 是 WindowsApps 假壳会被跳过）。
- **预算开启时**（`AGENT_DAILY_TOKEN_BUDGET>0`），巡检可折上当日账本：

```bash
docker compose -f deploy/docker-compose.yml exec agent python -m agent_service.api.budget --show
```

## 4. 检索并发闸（RAG_MAX_CONCURRENCY / RAG_QUEUE_TIMEOUT）

- 现象：`/qa`、`/answer`、`/materials/search` 排队超时返回 `503`，detail 「检索排队超时：处理中的请求已满，请稍后重试」，带 `Retry-After: 5`。
- 流式端点（`/qa/stream`、`/answer/stream`）**不返 503**：HTTP 200 + `event: error` 帧（message 同上一行），前端按 error 帧处理。
- 旋钮：`RAG_MAX_CONCURRENCY`（默认 4；`0`＝关闭排队不限并发）；`RAG_QUEUE_TIMEOUT`（默认 30.0 秒）。改 env 后 `docker compose ... up -d` 使容器拿到新值即生效（容器**重建**是必须的——进程环境变量不热更）；信号量按值懒重建、无启动期缓存，新值落进容器后不用再另做重启。
- `/health`、`/laws`、`/articles/lookup` 不进闸：服务过载时仍可探活与查条。
- 验收口径：eval L2 #8（并发占满→第二发 503/排队）与 #12（流式面→error 帧）按上述文案与帧形核对。

## 5. 成本闸（AGENT_DAILY_TOKEN_BUDGET）

- 账本 `data/usage.db`（agent 容器内落 `tlr_data` 命名卷），表 `usage_daily(day, tokens, calls)`，day＝UTC。
- **记账口径**：run 出口（正常 done / 澄清中断 / 异常三路）统一取出口时最新状态快照的 `usage` 与 `usage_extra` 两个通道**全部事件求和**（规划轮在 `usage`；地区识别 / 复核 / 答案生成在 `usage_extra`——一轮里每次模型调用都累计，不是取最后一次）；澄清中断轮已记的用量由澄清节点在 resume 续跑时清零，不重复入账；**异常出口可能少记未回写的最后一步**——口径如此，不是丢失。
- 写库失败只打 stderr 前缀 `[usage.db] 记账失败`、**不拦请求**；这个静默失效面靠 `--show` 被看见（§3 的巡检行；读失败同样打前缀并放行，`--show` 读失败非零退出）。
- 预算闸在 app 层：四个 run 端点进入前查当日（UTC）已用；已达 → 429 + `Retry-After`（到次日 UTC 0 点）。流式在**开场前**拦（不产生事件流）。`0`＝关（默认）；额度是全局的、不按 key。

## 6. 会话清理（AGENT_SESSION_TTL_DAYS，默认 30；0＝不清理）

判活 = 该 thread 最新 checkpoint 的 `checkpoint_id` 时间（uuid6，时间有序）。

dry-run（可在线，agent 容器内）：

```bash
docker compose -f deploy/docker-compose.yml exec agent python -m agent_service.agents.session_cleanup
```

`--apply` **必须停机**（SQLite 写者假设 + VACUUM 要独占）：

```bash
docker compose -f deploy/docker-compose.yml stop agent
docker compose -f deploy/docker-compose.yml run --rm agent python -m agent_service.agents.session_cleanup --apply
docker compose -f deploy/docker-compose.yml start agent
```

- 定时：宿主计划任务把上面三条串成一条（示例：每天 04:17）。
- 收尾打一行机器可读汇总 `[session_cleanup] mode=apply total=.. expired=.. rows=.. deleted=..`，可 grep 存档。
- 改代码后须 `deploy/build.sh` 重建 agent 镜像（CLI 随镜像走）。

## 7. 备份与恢复（deploy/backup.sh）

**备份**（冷备，分钟级停写；冷备窗口内问答不可用）：

```bash
bash deploy/backup.sh            # 产物 deploy/backup/<YYYYmmdd-HHMMSS>/
bash deploy/backup.sh --keep 3   # 打完只保留最近 3 份（防磁盘涨）
```

- 面 = `volumes/{etcd,minio,milvus}`（宿主 tar）+ 命名卷 `agent_tlr_sessions`（helper 容器 tar）；**不备份可重建物**（chunks/index 卷——重建配方见 README）。
- etcd/minio 打包期间不停：唯一写者 milvus 已停，二者静止。
- `deploy/backup/` 的 `*.tar.gz` 在 gitignore 面内；helper 镜像可 `BACKUP_HELPER_IMAGE` 指定（默认自动挑本机已有的 alpine → 服务镜像）。

**恢复**（自动建缺卷；结束起全栈）：

```bash
bash deploy/backup.sh --restore deploy/backup/<目录>
```

- 同名卷目录会改名留存 `.replaced-<stamp>`（人工确认恢复成功后自行删）。恢复＝停写 → bind 卷改名留存 → 解包 → 命名卷清空后解包 → 起全栈。
- **缺口提示**：`tlr_data` 命名卷（rag 侧 `data/documents.db` ＋ `data/uploads/`，即上传材料与文档库登记）**不在 R8 备份面**——重要上传材料需另行导出。
- 演练剧本（做过一轮全流程）：打备份 → 停栈 + 藏 `volumes/milvus` → `--restore` → 两服务 /health 全绿、带原 `session_id` 追问命中历史、`--keep` 连打清最老。

## 8. 密钥轮换（AGENT_API_KEYS）

1. 新 key 追加进 `AGENT_API_KEYS`（逗号分隔）→ 重启 agent；
2. 通知使用者换用新 key（旧 key 仍有效，无缝过渡）；
3. 移除旧 key → 再重启 agent（此后旧 key 立即 401）。

LLM / 判地区 / 复核三对 key 的轮换同理（改 `.env` → `restart agent`；rag 侧 key 改动 `restart app`）。
**上线前置**：换付费稳定源（免费/限流 key 不上线）；生成的 key 只发给使用者、不进聊天记录；**勾核 `AGENT_API_KEYS` 已设 + `/docs` 已 401** —— 设了以后 `/docs`、`/openapi.json` 与全部业务端点都要求 `X-API-Key`（不设＝整个面都开，`/docs` 不是独立隐患），探一下 `GET /docs` 返 401 即可确认。

## 9. 十二条口径（排障与对外解释前先看）

1. **单副本**：会话库是 SQLite（`tlr_sessions` 卷），写者假设单副本；限流计数与日额度记账同理。横向扩容前先换 Postgres checkpointer。
2. **异常 run 可能少记最后一步**：见 §5 记账口径。
3. **复核是辅助，不是保证**：末端复核受输出长度限制（多条依据时可能截断成坏 JSON 而**静默放行**），真正在拦的是「引用不支撑整篇降级」的代码规则；别把复核当合规保证。（范围界定见第 7 条，标定账见第 12 条。）
4. **web_search 的 egress**：该工具对模型**不可见**（不下发 schema），但分发面按精确名字可达——模型盲猜到名字即执行，未知工具回执还会把合法工具名单报出去。配了 `BOCHA_API_KEY` 就视为「可能外呼」；不需要网搜就别配 key。
5. **SSE 是过场流、无补发**：`/qa/stream` 的 `delta` 只是草稿（可能被复核整篇替换、中断与错误帧都不补发）；**`done` 帧才是权威答案**，断了重连不会续传，需要完整答案用非流式 `/qa`。
6. **LLM 未配置时的降级语义**：主管规划的模型（`LLM_API_KEY`）没配时，`/qa`、`/qa/stream` 不进图、降级为单轮检索问答（agent 侧不再调模型）；`/qa/resume`、`/qa/resume/stream` **不降级** —— 返回明确错误「规划模型暂不可用，无法恢复被中断的会话；请直接重新提问。」（非流式 `503`、流式 `error` 帧）。这是设计不是缺陷：恢复会话不能静默丢弃用户已选的地区，把「重新提问」的选择权交回用户。（口径登记：原 `docs/spec.md` §R11 记为「五条口径」、本条为第 6 条；该 spec 已按用户点名于 2026-10-10 删除、历史在 git；「登记而非删除」的口径模式沿用——对照 `RETIRED_PACKAGES`，现行清单以本节为准。）

7. **复核模型口径（2026-10-09 核对）**：`REVIEW_PATCH_NOTE` 里「检测力没证」的探针打的是**入口意图模型**（`tongyi-intent-detect-v3`），不是现役复核模型 —— 复核走 `AGENT_REVIEW_MODEL`，现役未配置该项、**回落主规划模型**（`qwen3-30b-a3b-instruct-2507`）。探针里「输出卡在 ~26 token、≥3 条截成坏 JSON」的现象**不能外推**到复核模型；第 3 条「多条依据时可能截断而静默放行」在现役模型上未重采样，「复核降级频发」的归因同样未按现役模型复测。

8. **提示词/回执层的已登记微瑕（2026-10-09 评审，定级非阻断、暂不修）**：
   - 零证据闸 `_NO_EVIDENCE_STOP_NUDGE` 说「手上一条证据都还没有」——只调过 `search_materials`（拿到过材料段）时它数的是法条证据，措辞与实况有缝；
   - `_SKIP_DUPLICATE` 说「参数与前面某一轮完全相同」，紧接着又说「上一轮的结果就在上面」——去重命中不一定是紧邻的上一轮；
   - 材料检索空命中时回执头恒为「材料#0」（命中时是首个命中段的材料序号），两个编号不同源，别当「第几次调用」读；
   - `NO_MATERIALS_NOTE`「本次会话没有上传材料」在「上传过、文件随后被清」的会话里半假（`doc_ids` 在、材料加载为空）；
   - 澄清题面「这个问题涉及具体的地区」按 `place` 非空触发（`cfg.clarify` 开时）：产地题（题面出现地名、适用国法）也会被问一次；回复库外地区名（如「广州」）会**静默回落**为只按全国法作答，不回执「该地区未收录」；region 提示词把 `place` 描述为「不进检索的线索」，未写它会触发澄清这一后果；
   - 澄清与 `place` 的这套用法是刻意设计（库小、"拿不准就给 ?"），以上按口径登记，口径变化时一并复核。

9. **降级组合边角（2026-10-09 作答侧修改引入的已知口径）**：`LLM_API_KEY` 未配、检索零命中、而材料/时效非空时，空检索短路不再生效，答案落到 `UNAVAILABLE_ANSWER`「（未配置大模型，下面只给出召回的法条）」——此时法条为空，材料/时效在载荷里但文案不提。仅整机未配模型的降级态才会出现，暂不修。

10. **agent 鉴权豁免里的 `/laws` 是死条目（2026-10-09 登记）**：`EXEMPT_PATHS`（`agent_service/api/auth.py`）与接口文档「鉴权与限流」段都写着「除 `GET /health`、`GET /laws` 外」要带 key，但 **agent 服务没有 `/laws` 路由**——带不带 key 打它都落 `404`（豁免先放行、再没有路由可匹配），`tests/test_agent_auth.py` 钉着这个行为；原 `docs/spec.md:24、31` 也这么写死（该 spec 已按点名于 2026-10-10 删除、历史在 git；同文件 :46 的 `/laws` 是 rag 侧真路由，不在此列）。无实害（不泄露任何面），按「登记而非删改」处理；要清就三处一起动（`auth.py` + 接口文档 + 测试断言）。

11. **round3 修复流登记（2026-10-10）**：`/reindex` 走模块级锁**串行**——并发调用排队、不再交错重建；**重建期间检索面不保证**（在途请求可能 500 / 暂态空答），原子交换（临时集合 + 换名）仍是后续独立卡。rag `/health` 新增 `milvus_live` 现场探针（ping 超时 2 秒，连不上即 `false`），`status` 从此 = 快照 ok **且**探针通过；agent 的 boot 判据仍只读快照字段 `milvus`（rag 活着但 Milvus 掉线时 agent 照常装配）。`has_collection` 把「连不上」与「集合不存在」都归 `false` 的吞异常按**留观**处理：调用面宽（`count` / `drop` / `describe` / `has_dense_field`、status 快照 `stale_reason`、检索降级 note），存活信号已由 `milvus_live` 兜住；要硬化就单开一卡、按调用点逐一裁定。

12. **复核阈值已标定（2026-10-10）**：`AGENT_REVIEW_MIN_SCORE` 默认值从占位 **0.6 改为 0.35**（`.env.example` 与接口文档已同步）。依据＝判官批：hop63_kimi 63 条降级前原文由 qwen3-30b 逐条判对错（单次、temperature 0），对上轨迹里 kimi-k2.6 打出的复核分——t=0.35 拦 6 条（3 真错 + 3 误杀、交付正确率 77.8%），旧 0.6 拦 16 条（5 真错 + 11 误杀、交付 65.1%）；该样本上 t>0 任何取值都低于无闸（t=0）的 82.5%，0.35 是「误杀最少且有真拦」的操作点。口径两条：①**复核分由 kimi 臂打出，现役复核模型（qwen3-30b）未重采样**（第 7 条的「未复测」仍成立）；②复核分度量「引用标签卫生」不度量「结论正确性」——6 条放行判错里 3 条 score=1.0，高分区结构性漏放，别把复核当正确性保证。
