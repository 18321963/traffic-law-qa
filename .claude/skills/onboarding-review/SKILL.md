# 上手审查（快速读懂 + 快速启动）

两条轴分开判、分开报。审查者假扮两种人，全程不许用「我熟这个仓」的后见之明。

## 轴一 · 快速读懂（假扮 30 秒访客）

只看 README 开头，逐问核对：**是什么 / 解决什么 / 效果如何 / 怎么跑** —— 四问在首屏与首节内能不能都答上。

- **关键信息不许被埋**：端口、入口、前提藏在代码块注释或长段后半句里 = 事故。先例：界面在 `:3000` 曾只出现在 compose 命令的注释里，用户找不到怎么启动前端（2026-10-11 修）。
- **层级**：结果与口径在前、实现细节在后；不许要求读者先读第三章才知道怎么跑。
- **数字与现状一致**：用例数、模型名、镜像体量、容器数、端口 —— 逐一拿仓库实测对照（`pytest --collect-only`、`docker images`、`.env.example` 等），README 里每个数都要有出处。
- **跨文档一致**：README ↔ `docs/04_接口文档.md` ↔ `docs/06_用户手册.md` ↔ `CLAUDE.md`；README 里的相对链接逐个核存在。
- **措辞**：对外文案没有「demo」（用「服务」「示例」）。
- 代码按名引用 README 小节（`README「入口」`这类自检文案）：动章节标题前 `grep -rn "README「"`，门禁会翻红。

## 轴二 · 快速启动（假扮照 README 从零跑的人）

- **逐条核真**：快速开始里每条命令 —— 路径存在、参数有效、端口属实、**预期输出/成功信号写了没有**（等几个容器 healthy、curl 什么、界面在哪个地址）。
- **最短成功路径**：从 clone 到「看见东西」几步？还能不能更少？非必需步骤有没有标「可选」。
- **前提写全**：环境要求、要花钱的（LLM key）、要下载的（模型权重、CUDA torch）、要代理的（外网）、镜像体量与首次耗时。
- **失败有出口**：连不上/被墙/没 key 时读者会遇到什么；文档有没有给判别句（代理 `127.0.0.1:7890`、pip 镜像源、容器 502/503 之辨）。
- **真跑优先**：不花钱的命令真跑一遍（`curl /health`、`pytest`、`--help`、`docker ps`）；要花钱/下大件的只做静态核对，报告里注明「未实跑」。

## 输出形状

- 开头一段总判：这个项目现在「几分钟能读懂 + 跑起来」。
- 按两轴分节，**逐条裁定**：每条给「动 / 不动」+ 为什么；「为什么不动」和「为什么动」同样要写；不凑数，没发现就明说没发现。
- 每条附证据（文件:行 + 怎么核的：读还是实跑）。
- 全量报告落仓外 `D:\projects\_tlq_onboarding_review_*.md`；聊天里给摘要与裁定表。

## 边界

- 不审效果数字的真假（评测的活）、不审代码结构（架构门禁与 code-review 的活）、不审界面使用体验本身 —— 但「界面入口在哪、怎么起」属于启动轴，要审。
