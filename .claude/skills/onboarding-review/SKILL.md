# 上手审查（快速读懂 + 快速启动）

三级时间盒逐级打分（PASS / PARTIAL / FAIL + 证据）；L1+L2 属**读懂轴**、L3 属**启动轴**，两轴分开报。审查者假扮陌生人，全程不许用「我熟这个仓」的后见之明；有条件就派无上下文子代理做「真陌生眼」探针 —— 只喂 README 原文、禁读仓库，收集它答不上来或答错的问题。

## L1 · 首屏 30 秒（读懂）

只看 README 开头，逐问核对：**是什么 / 给谁·为什么 / 效果如何 / 怎么跑** —— 怎么跑允许在首节之外，但入口节名必须一眼可导航；「活着吗」看近期活动信号（提交日期、效果数字的标注日期）。

- **关键信息不许被埋**：端口、入口、前提藏在代码块注释或长段后半句里 = 事故。先例：界面在 `:3000` 曾只出现在 compose 命令的注释里，用户找不到怎么启动前端（2026-10-11 修）。

## L2 · 全 README 2 分钟（读懂）

- **架构**：能不能在餐巾纸上画出系统轮廓；陌生术语首次出现处有没有定义。
- **边界**：做到什么 / 做不到什么要显著（如「联网检索 ⚠️ 未接线」）。
- **层级**：结果与口径在前、实现细节在后。
- **数字与现状一致**：用例数、模型名、镜像体量、容器数、端口 —— 逐一拿仓库实测对照（`pytest --collect-only`、`docker images`、`/health` 实读等），README 里每个数都要有出处。
- **跨文档一致**：README ↔ `docs/04_接口文档.md` ↔ `docs/06_用户手册.md` ↔ `CLAUDE.md`；相对链接逐个核存在。
- **措辞**：对外文案没有「demo」（用「服务」「示例」）。
- 代码按名引用 README 小节（`README「入口」`这类自检文案）：动章节标题前 `grep -rn "README「"`，门禁会翻红。

## L3 · 从零跑 5 分钟（启动）

- **前提写全**：环境（Python / Node / GPU）、要花钱的（LLM key）、要下载的（模型权重、CUDA torch）、要代理的（外网）、镜像体量与首次耗时。
- **逐条核真**：快速开始里每条命令 —— 路径存在、参数有效、端口属实、**预期输出/成功信号写了没有**（等几个容器 healthy、curl 什么、界面在哪个地址）。
- **最短成功路径**：从 clone 到「看见东西」几步？还能不能更少？非必需步骤有没有标「可跳过」。
- **首次成功**：有没有 hello-world 级、一发即见的验证点。
- **失败有出口**：连不上/被墙/没 key 时文档有没有给判别句（代理 `127.0.0.1:7890`、容器 502/503 之辨）。
- **真跑优先**：不花钱的命令真跑一遍（`curl /health`、`pytest`、`--help`、`docker ps`）；要花钱/下大件的只做静态核对，报告里注明「未实跑」。

## 输出形状

- 报告头：**首次理解用时 / 首次成功用时**（秒/分钟，或「未达成」）。
- 三级各给 PASS / PARTIAL / FAIL + 证据；再按级**逐条裁定**：每条给「动 / 不动」+ 为什么；「为什么不动」和「为什么动」同样要写；不凑数，没发现就明说没发现。
- 困惑点清单按严重度排序，每条四栏：位置 / 困惑 / 严重度 / 修法。
- 全量报告落仓外 `D:\projects\_tlq_onboarding_review_*.md`；聊天里给摘要与裁定表。

## 边界

不审效果数字的真假（评测的活）、不审代码结构（架构门禁的活）、不审界面使用体验本身 —— 但「界面入口在哪、怎么起」属于 L3，要审。
